# Repository-native agent harness protocol

Updated 2026-10-21. Purpose: prevent context loss, unsafe concurrent writes, and unverified completion. Works with one Codex agent or native subagents; optional tools must follow the same owner-approved workflow.

## Intake

1. Read root `AGENTS.md`, `current_context.md`, `project_progress.md`, `decisions.md` and `latest_session_work.md` in that order. Read architecture, roadmap and dated history only as task demands; search archived logs by targeted heading/ID rather than loading them all. Inspect `git status` before editing. Confirm which branch/dirty files belong to prior work; never clean/reset them blindly.
2. State the goal, constraints, acceptance criteria and impact radius. Reconstruct actual behavior by reading implementation + tests, not just the docs. Treat docs as durable context that may be stale.
   Before expanding the approved task or adding a prerequisite, verify its necessity against `decisions.md` and `project_progress.md`. If a material assumption is uncertain, stop **that branch** and ask the owner the specific question, with the reason and consequences. An agent's inferred precaution is not an owner-approved gate. Generic "continue" means the next agreed priority, not a new initiative. Continue independent work inside the agreed scope.
3. Split significant tasks into focused steps. Independent native subagents may inspect, test or review isolated scopes; designate one writer per file and one coordinating integrator. Preserve a single shared acceptance checklist.

## Execution & evidence

- **When Codex plugins are available:** use Superpowers skills for the relevant workflow step (e.g. systematic debugging, scoped plan, regression verification, independent review), sized to the requested change. For multi-file TypeScript/Python investigation, prefer Serena `find_symbol`/`find_referencing_symbols` via its REPL; avoid dumping huge files. Serena may need `activate_project` for `homeasy` in Codex Desktop because its MCP process does not necessarily start in this repository. Read Serena's initial instructions/session ID as needed. Its project configuration enables `no-memories`: write durable facts only to the owning `agent_docs/` file. A tool's suggestion of brainstorming or a worktree does not override the approved scope or the Git boundary below.
- Default to source inspection and offline/in-memory/temp SQLite fixtures. Do not invoke paid models, live scrapers, Facebook login, remote deployment or live database writes just to test a hypothesis. Preserve the browser-resource filters and Facebook session safeguards in `AGENTS.md`.
- Treat the dirty worktree as the owner's data. Do not commit, switch branches, force checkout, or delete datasets without the task requiring it. Be particularly cautious with `data/homeasy.db`, its WAL/SHM, account fingerprint, and session files.
- Update assertions when requirements have changed, but preserve behavioral coverage. Every defect fix should have a meaningful regression case where useful. Prefer `npm run lint`, `npm run typecheck`, `npm test -- --runInBand`, `npm --prefix webapp run test -- --run`, `npm run build:webapp`; run focused checks first.
- For **future canonical read-path changes or rollback**, verify list → map → detail → favorites → filtering/sorting → moderation → tracking and feature parity on isolated fixtures/snapshots first. The owner-approved global cutover already occurred on 2026-10-16; do not re-plan it or impose historical canary steps as a new prerequisite. Obtain the scope/permission relevant to any new live toggle.
- Database safety gate for **future owner-approved live writes/restores**: verified recent local `VACUUM INTO` snapshot + isolated writable restore with integrity/foreign-key checks + tested rollback procedure and the protected historical pre-cutover recovery point where relevant. Accepted data-loss tolerance (RPO) is 24 hours; it is not a guarantee unless the backup worker runs successfully and freshness is monitored. S3/off-device backup, encryption and remote restore are later hardening, **not a prerequisite for unrelated work**. Historic 2026-10-09 SQLite incident: see `data/incidents/sqlite-corruption-20261009/MANIFEST.md`. A broader inventory reset needs explicit scoped approval and a separate runbook.
- Use `sqlite_recovery_runbook.md` for detached restore rehearsal, local-only MVP cutover requirements, future external-copy design and gated production recovery. The runbook is an operator guide; do not execute its production steps during routine test runs.

## Durable checkpoint / exit

- `project_progress.md` owns the last verified phase status and next priority (single source of truth). `decisions.md` contains accepted constraints. `project_diary.md` and `history/` preserve older evidence. Keep `latest_session_work.md` bounded to the current session and immediate prior checkpoint: changed files, verified commands/results, findings, remaining risk, exact next action. Archive its previous content before replacing it. Do not duplicate production totals in other living documents.
- Update only the relevant owning files after significant work and before a conversation/context handoff. Include date, command outcomes, exact source file paths, and whether a live operation happened. Link to lengthy reports and archived evidence instead of pasting transcripts. Do not report tests as passed without running them. If a gate is blocked, state why.
- Keep instructions concise and link to code/tests rather than copying long source. New agent should be able to continue from disk without needing previous chat history.
