# Homeasy — план технической модернизации

**Согласовано владельцем 2026-11-21.** Цель — закончить надёжный каталожный MVP, навести порядок в разработке и выпускать проверяемые версии. Текущая архитектура остаётся модульным монолитом TypeScript/Fastify/SQLite с React Web/TMA, Mac-сборщиками и backend на VPS. Продуктовые изменения и операции с живыми данными требуют отдельного согласованного объёма.

Основные факты, доказательства и вход в систему — [`reports/homeasy-full-audit-20261121.md`](../reports/homeasy-full-audit-20261121.md). Решения и фактическое состояние по-прежнему находятся в `decisions.md`, `project_progress.md` и `latest_session_work.md`.

## Этап 1. Инженерный фундамент — выполняется

**Результат:** чистая история разработки с двумя длительно живущими ветками, автоматические проверки и возможность установить точно известную версию каждого опубликованного компонента.

- [ ] Сверить GitHub, локальный Mac и VPS. Сохранить все уникальные изменения в текущем dirty checkout, VPS и трёх detached worktree. Никогда не добавлять `data/`, секреты, raw-экспорты и временные результаты сборок.
- [x] Сформировать `develop` из девяти коммитов `codex/vps-migration-ready`, добавить отобранные и проверенные исходники, тесты, Web/TMA и документацию. Убедиться в чистоте рабочих деревьев и сохранности истории. `main` — production, `develop` — интеграционная ветка.
- [x] Внедрить GitHub Actions для Node 22, npm ci, typecheck, lint, Jest, Vitest, backend / Bright Data / Web / TMA сборок. Отсутствие секретов и обращения к live БД при CI обязательно.
- [ ] Настроить и проверить сборку Docker из конкретного Git SHA, записывать в релизном манифесте SHA, digest образов и идентификаторы Web/TMA сборок. В инструкции релиза зафиксировать проверенный rollback VPS и Pages.
- [ ] Проверить реальную привязку Cloudflare Pages к веткам, только затем удалить лишние удалённые ветки. Выкладка `develop` сама по себе не обновляет живые API/бот/SQLite и публичные сайты.

**Проверка 2026-11-21:** `develop` опубликован на `05dc919`, GitHub CI `44876869101` полностью прошёл; Web/TMA и Docker provenance доступны в артефактах. VPS прочитан по SSH: checkout на `codex/vps-migration-ready`, 20 локальных изменений, пять контейнеров работают. Для завершения остаются авторизованная проверка веток обоих Cloudflare Pages проектов, согласование текущей VPS-ветки с двухветочной моделью, проверка отката и безопасное удаление старых refs. Подробности в `latest_session_work.md`.

**Критерии приёмки:** GitHub хранит `main` и `develop`; локальные состояния и полезные изменения восстановимы; CI на `develop` зелёный; Docker/Web/TMA artefact можно сопоставить с коммитом; есть воспроизводимый rollback и понятный handoff. Изменение production требует отдельного релизного шага с проверкой данных и сервисов.

## Этап 2. Надёжность обработки данных

**Результат:** прозрачная, повторяемая воронка `source → ingest → AI → canonical → moderation → publication`.

- Проверить идемпотентность и повторные попытки Mac→VPS outbox, частичные ошибки AI и пакетной обработки, статус и причину удержания каждой карточки.
- Устранить проверенное дублирование логики на границах модулей и согласовать Zod/API DTO без переписывания работающих компонентов.
- Проверить миграции, SQLite WAL, конкурентные записи, backup/restore и rollback на изолированных копиях.
- Добавить информативные структурированные логи, метрики источников/ошибок и минимальные оповещения.

**Критерии приёмки:** каждое изменение статуса объявления объяснимо источниками; повторный импорт не создаёт неконсистентные записи; проверено восстановление данных и раннее обнаружение сбоя импорта.

## Этап 3. Качество пользовательского каталога

**Результат:** пользователи видят свежие объявления с рабочими фото, достоверной географией и контактами.

- Исследовать и исправить истекающие Facebook-фото, геоподписи и точные GPS с подтверждением исходником; учитывать расхождение 264→219 публичных записей по категориям причин.
- Оптимизировать Web/TMA, прежде всего загрузку карты (~1,21 МБ в ноябрьской сборке), и проверить реальные Android/iOS Telegram WebView и переходы в контактные приложения.
- Провести пилот каталога и измерить свежесть объявлений, успешность контактов и качество карточек перед запуском следующих marketplace-механик.

**Критерии приёмки:** ограниченный проверенный набор пользовательских сценариев проходит на живых устройствах, видимые дефекты данных измерены и исправлены, а по пилоту принято решение о дальнейших функциях.

## Принципы выполнения

Выполнять этапы последовательно с тестами и короткими подтверждёнными handoff. Без автоматического массового обновления объявлений, дорогостоящего сбора, переноса Facebook-аккаунта с Mac или необоснованной миграции на Kubernetes, микросервисы либо PostgreSQL. Для живого изменения данных, внешнего выпуска и платных операций использовать конкретную существующую авторизацию и проверяемый откат.
