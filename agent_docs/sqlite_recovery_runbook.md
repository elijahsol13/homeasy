# SQLite recovery / canonical rollback runbook

Updated 2026-10-15. Deployment: MacBook Docker Compose; all `bot`, `scraper`, and `api` mount `./data:/app/data` and use `DATABASE_PATH=/app/data/homeasy.db` with SQLite WAL. Incident precedent: `data/incidents/sqlite-corruption-20261009/MANIFEST.md`.

## 2026-10-18 host-side ingestion / Docker SQLite connection incident

After a successful host `ingestion:replay --commit` while Compose services held SQLite connections, the long-running API returned `SQLITE_CORRUPT` (errcode 11) and HTTP 500. The on-disk database passed independent host `quick_check` and container `quick_check`/`integrity_check`; a freshly opened connection inside that same container could read all rows. Restarting API restored HTTP 200 health/list/map; bot was also restarted. External list/map responses were 200. Root cause remains unproven; a stale connection or host/Docker bind-mount WAL coherence problem is suspected. Do **not** treat that log string alone as justification to replace the database, delete WAL/SHM, or restore an old snapshot.

For a subsequent **host-side live import**, first verify a protected backup and decide on a maintenance window; quiesce and stop API/bot/any other writer before importing against live `data/homeasy.db`, then restart them and verify full integrity/FKs plus health, list/map/detail and Telegram startup. Keep the current dataset and WAL/SHM intact; investigate this cross-OS concurrency failure on a detached fixture before introducing unattended production imports. This is an operational precaution drawn from the incident, not a verified permanent fix.

The CLI only accepts a non-symlink `.db` checkpoint directly under `data/backups/verified-checkpoints`, checks its SHA-256 and never opens `data/homeasy.db` or touches a Compose service.

The script copies that checkpoint into a new private OS temp directory, enables WAL, commits a synthetic change and keeps the writer open. It verifies that the committed change is **absent** from the copied main `.db` alone but **present** when the saved `.db + -wal + -shm` triplet is replayed, with `integrity_check=ok` and no foreign-key violations. It copies the three incident artifacts into a simulated stopped volume, preserves all three separately **before replacement**, installs a fresh copy of the verified snapshot without old `-wal/-shm`, confirms the incident change is absent, schema/table counts match and a new write succeeds. The protected source hash is checked again. This is a filesystem/WAL rehearsal, **not** a real unclean process crash, production Compose shutdown or production restart.

## Backup host watchdog (installed 2026-10-14)

### Telegram admin alerts (test-only live send passed 2026-10-15; automatic scheduling pending)

The portable host watcher now supports `npm run backup:monitor -- --telegram`. This **sends real Telegram messages** when the backup is warning/critical or recovers from a previously notified problem; it is deliberately **not part of the installed macOS LaunchAgent**, which retains its original `--notify` behavior. Do not invoke `--telegram` casually while diagnosing a sandboxed Docker socket: if Docker inspection is denied, the watcher interprets that as `critical`. First verify the host's normal Docker permissions with the read-only `npm run backup:monitor -- --json`. Do not include `--telegram` in offline rehearsals.

This command must run on the **Docker host**, from the project directory, on a recurring schedule (every 30 minutes is recommended), using Node >=22, access to `docker inspect homeasy-backup` and read access to the local backup directory. Its current process reads `BOT_TOKEN` and comma-separated `ADMIN_IDS` from the host's existing `.env`; the Telegram bot must already have received `/start` in each administrator's private chat. It calls the Telegram HTTPS API directly even if Homeasy's bot/API containers are down. Configure a Linux `systemd` timer or cron on the eventual always-on server to execute `node dist/database/backup-monitor.js --telegram` with the correct `WorkingDirectory`, `DATABASE_PATH` and Docker CLI availability; install/configure that scheduler only when the host is selected. **Do not put this watchdog inside the Compose stack it is monitoring.** The backup worker remains free of Telegram tokens.

The same warning >18h, critical >24h/stopped Docker, six-hour repeat and single recovery rules apply; each admin uses an independent, ignored `data/.backup-monitor-telegram-<id>.json` marker (mode 0600). An acknowledged Telegram `ok=true` response advances only that admin's marker. A failed or timed-out request is retried at the next interval; an uncertain API response can theoretically produce a duplicate. **Live transport acknowledgment is verified** for two clearly labeled synthetic alerts on 2026-10-15; offline transition/retry coverage remains in `tests/backup-telegram.test.ts`. Automatic monitoring still needs host-side scheduling and eventual owner confirmation of message visibility. A powered-off/isolated host cannot send its own outage alert; later add an **external** heartbeat monitor to detect complete host/network outages. In particular, Telegram alerts do not replace off-device backups.

Inspect current state with `npm run backup:monitor -- --json` from the project root. `src/database/backup-monitor.ts` reads Docker container `homeasy-backup` state and the latest verified local snapshot, without connecting to SQLite or sending network requests: **warning after 18 hours** without a fresh backup or an unready healthcheck, **critical after 24 hours**, missing snapshots, or a stopped/uninspectable container. A Docker-reported unhealthy state is critical even when the snapshot is still recent.

Install/reinstall the per-user macOS LaunchAgent with `bash scripts/install-backup-monitor.sh --install` **after** `npm run build`. The installed `~/Library/LaunchAgents/com.homeasy.backup-monitor.plist` runs on login and every 30 minutes, with absolute Node/Docker paths; `launchctl print gui/$(id -u)/com.homeasy.backup-monitor` checks its status. Review ignored `data/backup-monitor.log` for problems. `--notify` emits local macOS Notification Center alerts when status degrades, repeats after six hours, and sends one recovery notification. Ignored `data/.backup-monitor-state.json` deduplicates notices. To disable: `launchctl bootout gui/$(id -u) ~/Library/LaunchAgents/com.homeasy.backup-monitor.plist` (the plist remains unless manually removed).

**Observed:** installed LaunchAgent last exit code **0**, subsequent CLI monitor `status=ok`, worker running/healthy, backup age ~0.8 h (later ~1 h). The first LaunchAgent invocation incorrectly treated Docker as unavailable due to launchd's limited PATH; pinning absolute Docker and Node paths and reinstalling resolved the false alarm. **A Codex sandboxed CLI inspection can also report `critical/unavailable` if denied access to `docker.sock`: verify from the normal host context or with explicitly approved read-only Docker inspection before treating it as a real backup outage.** Repeated read-only inspection with Docker access on 2026-10-14 returned `running/healthy`, `status=ok`, age 1 h. Warning/critical classification is covered by unit tests, but **a real outage notification or sleep/wake behavior has not been tested**. A sleeping/offline Mac cannot monitor or maintain a 12-hour recovery-point schedule; GUI permission to show notifications may also need checking.

**Safe offline alert rehearsal:** `npm run backup:monitor-rehearsal` runs the same assessment and notification-marker logic against synthetic snapshot timestamps and a temp-only marker, stubbing out macOS delivery. Verified 2026-10-14: **11 scenarios PASS**, including first warning at >18h, critical at >24h, six-hour repeat, simulated failed delivery/retry and single recovery. It never inspects Docker, reads production backup data, posts a real notification, or changes `data/.backup-monitor-state.json`. The test proves dispatch/deduplication behavior; a supervised host GUI check is still required to prove Notification Center visibility. `npm run build` refreshes the installed monitor's existing JS target; no LaunchAgent reinstall was performed in this rehearsal.

## Preconditions (operator checklist)

1. Identify whether the path is the **live** `data/homeasy.db`; preserve its `-wal` and `-shm` companions. No automated agent should modify these without an explicit, scoped recovery request.
2. Verify a recent `src/database/backup.ts` snapshot exists, with a known restore point. `npm run db:backup` creates a SQLite `VACUUM INTO` point-in-time snapshot and rotates local backups (default **21**); it is a real file-changing operation. The snapshot source follows `DATABASE_PATH` and the default backup directory is `<database directory>/backups`. Check the effective path in each environment before invoking it; do not point a rehearsal at the live path by mistake. `tests/backup.test.ts` uses temporary fixtures.
3. The Compose `backup` service runs the minimal Node `api-runner` image, mounts only `./data`, needs no external credentials, makes a snapshot on startup and every **12 hours** after success, and retries failures after **30 minutes**. The worker's health check marks backups older than **24 hours** unhealthy. The scraper also makes pre-maintenance snapshots and the bot `/backup` command may make manual ones; all use one shared 21-snapshot top-level rotation. **Deployed 2026-10-14 and observed healthy:** first live-db backup logged as verified (58,560,512 bytes); detached host and isolated Docker writable restores and a real listening API from a separate restored copy passed. See `reports/backup-compose-restore-20261014.json` and `reports/backup-docker-api-and-monitor-20261014.json`. The second scheduled backup remains unobserved. Monitor `docker compose ps backup` and `docker compose logs backup`; a host LaunchAgent now adds local notification monitoring, subject to a running, awake Mac and successful macOS notification delivery.
4. **Owner decision:** local MacBook backups are acceptable for MVP; tolerated recovery point loss is **up to 24 hours**; off-device S3 replication is deferred. The scheduled 12-hour interval is intended to provide margin toward the 24-hour goal when Docker and the MacBook are continuously running, but cannot guarantee it during host shutdown, full disk, repeated backup failures, or paused Compose. `./data/backups` on the same disk does **not** survive disk loss, theft or host failure. Actual RPO still needs continued monitoring; the initial detached restore passed. The separately verified pre-canary checkpoint is `data/backups/verified-checkpoints/homeasy_precanonical_verified_20261014T104154Z.db` (SHA-256 in the evidence report), in a subdirectory untouched by top-level rotation. Keep it until cutover/parity acceptance and preserve future pre-cutover snapshots separately.

Store the decryption identity separately from the backup destination and exercise decryption in a scratch directory. Do not put secret keys into repository files, command arguments or logs. `age` installation and recipient setup have **not** been verified on this machine.
- Suggested *provisional* retention: seven daily and four weekly off-device recovery points; retain a separate pre-cutover snapshot until the canary window closes. Do not blindly mirror the local 21-file pruning policy to remote storage. Alert on missing/failed transfers, absent new recovery points and checksum mismatches. Finalize thresholds and remote access with the owner before enabling.
- Recovery acceptance is measured from a **freshly downloaded and decrypted** archive, not merely from a local copy. Check SHA-256 **before and after** the transfer/decryption, run `PRAGMA integrity_check` and `PRAGMA foreign_key_check`, and verify critical data invariants. Never store an unencrypted restored DB in a cloud-synced folder.

## Safe, detached restoration rehearsal

1. Work only under a **new scratch directory**, never under `data/`; copy a verified snapshot `homeasy_backup_*.db` to that directory. Keep the original snapshot intact.
2. Record the snapshot SHA-256 (`shasum -a 256 <snapshot-file>` on macOS). Open the copied file with `node:sqlite` in read-only mode, check `PRAGMA integrity_check` returns `ok` and `PRAGMA foreign_key_check` returns zero rows. Inspect canonical and user-table counts and confirm the app's current schema migration expectations; verify source history, moderation, favorites and tracking links. If this tests a remote archive, download and decrypt it into scratch first and compare SHA-256.
3. Exercise the restored copy as a *writable* independent database, then point a disposable API test environment at it and run list, detail, map and favorite smoke cases. Keep credentials and notifications disabled in this isolated exercise. Record results and the original snapshot checksum.

Automated minimum: `npx jest tests/backup.test.ts tests/backup-worker.test.ts --runInBand --silent`; this does not replace recovery rehearsal with actual Docker volume and data.

Graceful shutdown now calls `stopWorkerAndWait()` before closing SQLite in the standalone scraper and combined service. It prevents the local connection from closing while a worker operation is still running, but **does not forcibly cancel or bound the duration of active browser/HTTP work**. Docker's scraper `stop_grace_period: 120s` can still expire and result in SIGKILL if an operation hangs. A true Docker rehearsal must establish whether the configured grace period is sufficient, whether WAL is replayed, and that a blocked scraper cannot delay a restore indefinitely.

## Production restoration (requires separate approval)

1. Freeze writes and notification dispatch; set `CANONICAL_ALERTS_ENABLED=false` on the relevant workers if recovering after canary activation. Stop scraper, bot and API gracefully using Docker Compose and verify all containers have stopped. The tunnel may remain up but should show unavailable during the maintenance window. Do not copy an active raw WAL database as the backup.
2. Preserve the current `homeasy.db`, `homeasy.db-wal`, `homeasy.db-shm` together in a timestamped incident directory **before** replacing anything. Record snapshot location and integrity results.
3. Install only the independently validated SQLite snapshot at the expected `./data/homeasy.db` path; do not carry over old WAL/SHM files. Check permissions and start the API first; verify integrity, migrations, list/detail/map/favorites, then resume bot and scraper.
4. If canonical reads are unstable, set `LISTING_READ_PATH=legacy` **and clear the `CANONICAL_READ_CANARY_TELEGRAM_IDS` allowlist** in the deployment environment and restart API/bot as appropriate. Disable the canonical alert workers on **both** the scraper and active Telegram delivery service; verify users are receiving legacy IDs and actions. An allowlisted user otherwise remains canonical despite the global switch. Preserve parity logs. Restoring the DB and changing read path are separate rollback mechanisms.

## Cutover acceptance criteria (proposed, owner has not approved)

- During the controlled two-account Telegram canary (admin + regular), require **zero** mismatched listing identities, incorrect favorite/report targets, duplicate/unintended notifications, or broken deep links in the acceptance sample. Check list, detail, map, sort/filter, contact, tracking, moderation and hidden-listing 404 behavior. Validate the legacy fallback separately.
- Record a baseline for 404 and 5xx ratios and p95 list/detail API latency on the same device/network and request mix **before** setting any release thresholds. Suggested starting guard: new unexpected 404s = zero in the canary, 5xx < 1% in a rolling 15-minute window and p95 < 2 seconds with no >2× degradation from baseline. These are **proposals**, not observed performance or agreed release criteria. Define trigger, measurement source and rollback authority before rollout.
- For the **owner-approved local-backup MVP**, confirm a recent locally verified snapshot, SHA-256 checksum, successful detached restore, current Docker Compose image tags and an agreed maintenance window before global read-path migration. Off-device S3 backups, encryption and verified remote restore remain later hardening, but are **not a prerequisite for the MVP canary** under the accepted 24-hour RPO tolerance. Run real Telegram sends and Docker restart/restore only in that controlled window.
