# Homeasy: запуск сбора через Telegram и VPS — проект решения (2026-11-09)

**Статус: 30-дневный период по умолчанию утверждён владельцем и реализован локально; архитектура worker/Telegram остаётся предложением.** Для ближайшего ручного запуска владелец отдельно выбрал последние две недели (26.10–09.11.2026), начиная с трёх самых результативных групп по отчёту 18 октября. Платный сбор, AI-запросы, production ingest и деплой в рамках локальной подготовки ещё не выполнялись.

## Уточнённая задача владельца — 2026-11-09

- Собрать **до 1000 Facebook-постов из уже существующего реестра групп**, не добавлять и не обходить «1000 групп». Число 1000 — лимит собранных записей на один запуск, а не обязательный результат из 1000 новых, уникальных или опубликованных объявлений.
- Сбор запускается **только владельцем вручную**. В Telegram-админке нужны удобные команды для запусков разного масштаба (предлагаемые пресеты 100/500/1000 постов) и наблюдения за прогрессом/запросами. Расписание — отложенная отдельная задача.
- После успешного сбора должна **автоматически** идти существующая цепочка AI-классификации, извлечения/нормализации, дедупликации и canonical ingest, чтобы подходящие записи могли появиться в каталоге с учётом обычных правил публикации и модерации.
- В будущем аналогичный интерфейс будет нужен для других скраперов, но текущая реализация охватывает только Bright Data / Facebook. Владелец собирается самостоятельно контролировать количество запросов при первых запусках; денежный потолок и реальный баланс провайдера **не назывались и не проверялись**.
- Владелец **утвердил стандартный период сбора 30 дней** и отдельно потребовал **всегда явно сообщать о важных ограничениях**, в особенности если окно по умолчанию не охватывает старые записи. Посты недельной давности должны попадать в выборку.

## Проверено в текущем состоянии

- VPS `ovh` (`/home/ubuntu/homeasy`) работает: контейнеры API, Telegram-бота, бэкапа и туннеля были доступны при read-only проверке 2026-11-09. На хосте отсутствует `node`; в работающем контейнере бота нет `scripts/`, а в production-образе нет `ts-node`. Скрипт Bright Data на VPS прямо сейчас запустить как штатную контейнерную задачу нельзя.
- `npm run brightdata:test:groups -- --full` — существующий бесплатный dry-run. Скрипт требует `--submit` для платных запросов. `BRIGHTDATA_RECORD_BUDGET` ограничен 1–1000, `BRIGHTDATA_PER_GROUP_LIMIT` задаёт потолок на группу. Поддерживаются `--pilot`, `--adaptive`, `--resume-pending`.
- **Локально изменено:** по умолчанию скрипт запрашивает календарные даты от **сегодня минус 30 дней до сегодня включительно** по времени Камбоджи. Это 31 календарная дата на границах, чтобы охватить все посты за последние 30×24 часа при провайдерском формате YYYY-MM-DD; недельные записи входят. Ранее было **вчера → сегодня**. Для произвольного окна можно указать обе переменные `BRIGHTDATA_START_DATE` и `BRIGHTDATA_END_DATE`; одна переменная или ошибочная дата отвергается. Режим `--shadow-single-group` по-прежнему требует явно заданные одинаковые даты. Не путать этот период **запроса к провайдеру** с отдельным правилом 30-дневной публичной видимости canonical по оригинальной дате публикации.
- В конфигурации: 23 Facebook-группы, из них 16 разрешены для Bright Data, 6 приватных отложены для Camoufox, 1 доступ не определён. Бесплатный dry-run для предела 1000 записей (`BRIGHTDATA_RECORD_BUDGET=1000 BRIGHTDATA_PER_GROUP_LIMIT=63 ... -- --full`) успешно построил план на **16 групп**; это максимум запрашиваемых записей, а не 1000 различных групп и не гарантия получения 1000 новых объявлений.
- `npm run brightdata:classify` выполняет AI-классификацию/извлечение и canonical ingest **по умолчанию**. Без записи в БД: `--classify-only`. Для привязки к конкретному сбору использовать `BRIGHTDATA_SOURCE_RUN_ID`, не автопоиск «последнего»; требуется убедиться в целостности всех ответов провайдера.
- Поступившая canonical запись может быть дублем, нерелевантной, устаревшей или требовать модерации. «В базе» не означает «опубликована в каталоге».
- Facebook/Camoufox по утверждённому проектному правилу работает только на Mac с его зафиксированной browser identity; перенос браузера на VPS запрещён. Khmer24 с VPS остановлен из-за Cloudflare ASN denial, пока не решён разрешённый доступ.

## Рекомендованная схема

1. **В Telegram:** `/admin` → `Сбор данных` → `Bright Data / Facebook` → объём `100 / 500 / 1000 постов`, период (**утверждённый стандарт — 30 дней**; можно указать другой допустимый период). Исходные группы — существующий реестр с разрешённым маршрутом `BRIGHTDATA`; новые группы оператор не вводит. Предпросмотр явно показывает **точные даты**, число групп, максимум запросов/постов, исключённые группы, отсутствие гарантии 1000 новых публикаций и предупреждение о двух видах расходов: Bright Data + AI. Точная сумма выводится лишь при наличии достоверных тарифных данных; неизвестная сумма честно помечается как неизвестная. Только после явного подтверждения администратором запуск переходит в очередь. Действия: `Статус`, `История`, `Отменить следующие запросы`, `Повторить обработку скачанного`.
2. **На сервере:** существующие Telegram-бот, SQLite и Docker Compose; отдельный небольшой worker для задач коллекции, без новой внешней очереди. Бот после проверки `ADMIN_IDS`/роли записывает задание с неизменяемыми параметрами и ключом идемпотентности; worker исполняет только известные сценарии, без произвольного shell из Telegram. Код существующих TS-скриптов и правил переиспользуется (потребуется включить исполняемую часть в production-сборку: сейчас `scripts/` и `ts-node` там нет).
3. **Pipeline:** `queued → preflight → collecting → provider_pending/receiving → raw_saved → validating → classifying → extracting → canonical_ingest → finished` либо `needs_attention/failed/cancelled`. Фиксируются provider snapshot ID, локальный raw run ID, число уже отправленных POST, полученные записи и итог AI/ingest. Для 1000 записей при текущих 16 разрешённых группах бесплатный предварительный расчёт показывает до **16 запросов** и лимит **63 записи/группу** с общим пределом 1000. Фактическая выдача может быть меньше. Автоматических дополнительных платных запросов «добрать до 1000» не делать.
4. **Восстановление и гейты:** один активный платный job Bright Data; после `202` восстанавливать snapshot через GET/download без повторного POST. Если процесс оборвался между POST и сохранением provider ID, отмечать неопределённость и требовать ручной разбор до следующей отправки. При неполном наборе ответов не запускать AI молча, чтобы не выдавать частичную загрузку за полную. Остановка действует до следующего POST, уже принятый запрос может завершиться. Отдельный replay по сохранённым raw не создаёт запросы Bright Data. До canonical ingest — штатный backup/проверка DB и миграций. Никакого автоматического расписания.
5. **Итоги в боте:** запрошено и фактически получено постов; число отправленных/максимальных запросов; готовые/ожидающие snapshots; уникальных после дедупликации; supply/demand/irrelevant; AI успешно/с ошибками; принято canonical; pending/moderation; реально видимых в каталоге; расходы, только если достоверно доступны от провайдера. Ошибка сопровождается безопасным следующим действием.
6. **Для остальных источников:** текущий UI может показывать секцию будущих источников без активных кнопок запуска. Camoufox/Facebook остаётся **на Mac**, Khmer24 на VPS остаётся заблокированным Cloudflare ASN denial. Сценарии других источников и расписание — последующие самостоятельные задачи, без преждевременных общих адаптеров.

## Почему отдельный worker

Прямой вызов CLI из Telegram-обработчика кажется короче, но при перезапуске бота теряются промежуточное состояние и информация о возможном платном snapshot. Постоянный worker с журналом jobs позволяет докачать уже оплаченный результат, продолжить AI-обработку и не оплачивать тот же запрос повторно. В рамках MVP использовать существующую SQLite/API и Docker Compose, без Redis и новых внешних сервисов, если нагрузка не потребует их.

**Рассмотренные подходы:** (A) прямой запуск существующего CLI из обработчика бота — меньше кода, но слабо переживает перезапуски и возможные дубли POST; (B) SQLite jobs + отдельный worker — рекомендуемый компромисс для платных snapshot, статуса и возобновления; (C) Redis/внешний task-сервис — отдельные процессы, настройки и эксплуатация без необходимости для текущей нагрузки. Выбор B пока **предложение**, не подтверждение владельца.

## Порядок реализации после согласования

1. Согласовать **архитектуру worker/Telegram** (стандартные 30 дней уже утверждены и локально реализованы). Снять бесплатный dry-run план с текущего реестра на VPS перед каждым подтверждением платного задания; не блокировать проект придуманным денежным потолком, но явно показывать, что текущие тариф и остаток лимитов пока не проверены.
2. Собрать production worker с теми же TS-правилами парсера; сохранить старые CLI как низкоуровневый интерфейс, дать worker явные run IDs и последовательное возобновление после сбоя.
3. Реализовать журнал заданий, админские API/кнопки Telegram, права, предпросмотр, подтверждение стоимости, отчёт о результате, отмену и восстановление.
4. Проверить на isolated fixture/копии БД: dry-run без API-запросов; имитацию `202 + snapshot_id`; обрыв между POST и download; повтор webhook; duplicate job; классификацию и canonical ingest повторно без нового POST; реальную модерацию/публикацию. Только затем — ручной небольшой live pilot в утверждённых денежных лимитах.

**Нерешённое:** требуется согласие на **схему worker/Telegram**, а не на уже принятый 30-дневный период, перед продуктовой реализацией. Цель **1000 постов из существующих групп** и **только ручные запуски** уже уточнены владельцем. Стоимость Bright Data/AI и остатки лимитов сейчас не подтверждены, поэтому каждый live запуск требует отдельного предпросмотра числа запросов и явного подтверждения в админке. Сам по себе этот документ ничего не запускает.
