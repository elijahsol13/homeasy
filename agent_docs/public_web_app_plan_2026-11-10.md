# Homeasy: публичное Web App на поддомене RustyCat

**Статус:** подробный план реализации для следующего Codex-диалога, 2026-11-10. **Реализация и продакшен-деплой публичной версии не подтверждены.** Предложенная владельцем схема: публичный Web App — `homeasy.rustycat.cc`, Telegram Mini App — `tma.rustycat.cc`, общий API — `api.rustycat.cc`. Это проект маршрутизации; DNS и действующие подключения не менять без проверки и отдельного этапа релиза.

## Цель и границы

Открыть каталог Homeasy напрямую в обычном браузере без Telegram, сохранив возможности пользовательского Mini App: ленту, поиск и фильтры, сортировку, карту, карточку объекта и фотографии, «Saved», открытие контактов и ссылок, обработку ошибок. Запустить аналитику посещений, действий и воронки до нажатия на способ связи. Подключить новый поддомен через Cloudflare Pages.

На этом этапе не проектируем новый продукт, не переносим API/SQLite, не создаём вторую систему объявлений или скрапер и не открываем модерацию анонимным пользователям. Авторизация, синхронизация «Saved» между устройствами, PWA/offline и полноценные SEO-страницы каждого объявления — отдельные возможные последующие этапы.

## Что подтверждено текущим репозиторием

- `webapp/` — React/TypeScript/Vite. `webapp/src/App.tsx` уже содержит ленту, фильтры, сортировку, карту, модальное окно объявления, сохранённые объявления и контакты; основной контент запрашивается через `webapp/src/services/api.ts`.
- API на Fastify (`src/modules/api/`) и единая SQLite остаются на существующем VPS; фронтенд размещается на Cloudflare Pages. Текущий Telegram Mini App расположен на `homeasy.rustycat.cc`. Подтверждённое решение проекта: Pages production branch `main`.
- Публичный каталог, карточки, фильтры и карта поддерживают запросы без Telegram `initData`; `favorites`, `listings/:publicRef/view` и `listings/:publicRef/interest` требуют Telegram-аутентификации. Публичный `/me` возвращает гостевой режим. Модерация доступна лишь аутентифицированному администратору.
- `webapp/src/services/telegram.ts` содержит вызовы Telegram WebApp, а `webapp/index.html` безусловно загружает Telegram SDK. Отдельный браузерный режим следует сделать явным.
- PostHog JS уже подключён (`webapp/src/services/analytics.ts`), но инициализация зависит от `VITE_POSTHOG_API_KEY`; наличие рабочего production-ключа и полноту существующих событий необходимо проверить перед запуском. В коде уже фиксируются клики на Telegram/WhatsApp/телефон. Наличие события не подтверждает состоявшийся контакт/сделку.
- `src/modules/api/routes/tracking.routes.ts` направляет текущие специальные `/r/:slug` ссылки преимущественно в Telegram. Существующую атрибуцию и работу таких ссылок необходимо сохранить.
- Рабочее дерево содержит чужие незакоммиченные изменения и файлы данных: при реализации требуется не затронуть их; отдельно отложить любую работу со скраперами, AI, базой и VPS, не нужную для веб-доступа.

## Предлагаемая архитектура

```text
Пользователь без Telegram                  Пользователь в Telegram
        |                                          |
homeasy.rustycat.cc (цель)                  tma.rustycat.cc (цель)
    Cloudflare Pages                          Cloudflare Pages
        |                                          |
        +---------- общие React-компоненты --------+
                       |  режим среды
                       |
                 api.rustycat.cc
                    Fastify API
                       |
                 текущая SQLite
```

Использовать **один репозиторий и общие компоненты**, с небольшими адаптерами `web`/`telegram` для запуска, навигации, контактов, авторизации и сохранений. Новый Web App разместить как отдельный Pages-проект (или отдельный deployment-профиль) из того же `webapp/`, с отдельным адресом, конфигурацией и возможностью отката. Избежать дублирования компонентов и API. Перед реализацией подтвердить параметры имеющегося Pages-проекта и способ разделения билдов.

В браузере по умолчанию включён **гостевой режим**: читать, искать, сортировать, просматривать карту и открывать поддерживаемые контакты можно без регистрации; «Saved» хранится локально в браузере. Сохранения не синхронизируются между браузерами/устройствами и могут исчезнуть после очистки данных. В Telegram остаётся существующий серверный список избранного. Обе поверхности используют одинаковые DTO, фильтры и список объявлений.

## Этапы реализации и проверка готовности

### 1. Публичный браузерный режим и UI

**Работы:** определить платформу по реальному Telegram `initData`/контексту с безопасной деградацией; не инициализировать Telegram bridge и не загружать SDK в отдельном Web build. Извлечь малую платформенную прослойку из `App.tsx`, `telegram.ts`, `contact-actions.ts` и сервисов API. Не допустить гостевых вызовов API, которые гарантированно отвечают `401`. Добавить адаптивную компоновку для больших экранов, корректные тач- и клавиатурные действия, доступную навигацию и управление модальным окном/картой. Сохранить мобильный вид Mini App.

**Приёмка:** чистый браузер без Telegram открывает каталог, детали и карту без JS-ошибок и повторных `401`; все основные действия работают на телефоне и десктопе; существующий запуск в Telegram не регрессировал.

### 2. Паритет функций гостя

**Работы:** реализовать через единый интерфейс хранилища два бэкенда «Saved» — серверные избранные для Telegram и `localStorage` для публичного Web App (по `publicRef`, с дедупликацией и защитой от устаревших/удалённых объектов). Синхронизировать сердечки в ленте, карте, деталях и вкладке Saved. Для ссылок контактов предусмотреть обычные `https:`, `tel:`, копирование номера и работающий выход к WhatsApp/Telegram на устройствах без установленного приложения там, где это позволяет ссылка; не скрывать другие способы связи из-за отсутствия Telegram. Запретить анонимным пользователям админские действия и серверные Telegram-only интересы.

**Приёмка:** выбранное объявление остаётся в Saved после перезагрузки в том же браузере; видимость и статус совпадают между вкладками, а удалённые объявления обрабатываются корректно; ссылки связи работают без Telegram-авторизации; анонимный пользователь не может делать действия администратора.

### 3. URL, навигация и возможность поделиться

**Работы:** URL для карточки `/listing/:publicRef`, открытие карточки при прямом переходе, browser Back/Forward и возврат к ленте/карте. Уточнить URL-представление фильтров и параметры кампаний `utm_*`, обеспечить работу URL после F5 через существующий Pages SPA fallback. Дать копирование ссылки на объект. Предусмотреть отдельные web-landing ссылки для маркетинга и сохранить поведение существующего Telegram `/r/:slug` без внезапного перенаправления аудитории.

**Приёмка:** ссылка на конкретную карточку открывается из любого браузера без Telegram; история браузера и обновление страницы работают; источник кампании атрибутируется; старые Telegram-ссылки остаются рабочими.

### 4. Аналитика PostHog и отчёты

**Работы:** проверить текущую конфигурацию PostHog и сквозной поток событий в dashboard; добавить обязательный признак `surface=web|telegram` и версию релиза. Для гостей — анонимный стабильный идентификатор устройства/браузера от PostHog, без создания фиктивных Telegram-пользователей. Уточнить сбор referrer/UTM, зафиксировать явные события и единый словарь свойств. Строить события по **фактическому действию**, исключать дубли от React StrictMode и повторных сетевых запросов.

Минимальный словарь событий:

| Событие | Когда фиксировать | Полезные свойства |
| --- | --- | --- |
| `page_view` / `app_opened` | вход и корректная смена клиентского URL | surface, landing, UTM/referrer, release |
| `catalog_loaded` | успешно получена первая выдача | city, count, duration |
| `search_used`, `filter_applied`, `sort_changed` | изменено условие поиска | тип фильтра, число выбранных значений, сортировка; без текста свободного поиска |
| `map_opened`, `map_marker_clicked` | работа с картой | city, listing_ref при клике |
| `listing_opened` | человек открыл карточку | listing_ref, source(feed/map/saved), позиция |
| `favorite_added`, `favorite_removed` | изменение Saved | listing_ref, surface |
| `contact_lead_clicked` (существующий контракт; проверить реализацию) | нажат Telegram/WhatsApp/телефон | listing_ref, channel, source(feed/detail) |
| `outbound_source_clicked` | переход на первоисточник | listing_ref, source |
| `client_error` | критичный сбой загрузки/API | stage, код ошибки; без личных данных |

Собрать в PostHog dashboard: уникальные посетители, просмотры/сессии, новые и вернувшиеся, web vs Telegram, источники и кампании, топ карточек, использование фильтров/карты/Saved, конверсия `вход → каталог → карточка → нажатие контакта`, потери по шагам и ошибки. **Клик по контакту — намерение связаться, не доказательство отправленного сообщения.** Аналитика не должна получать телефоны владельцев и посетителей, Telegram username/имена, полный поисковый текст, секреты; отдельно проверить текущую передачу Telegram профиля в `identifyTelegramUser` и настройки сбора IP, срока хранения, политики конфиденциальности и согласия согласно применимым требованиям.

**Приёмка:** на тестовом проекте/окружении видно по одному ожидаемому событию за действие; обе поверхности различаются в дашборде; браузерный посетитель проходит полную воронку без логина; события не включают чувствительные значения; отсутствие PostHog не мешает работе сайта.

### 5. Проверки и качество перед релизом

**Работы:** добавить точечные frontend/API тесты на режимы, избранное, навигацию, гостевые запросы, аналитику и атрибуцию; провести браузерные E2E на Chrome/Safari/Android/iPhone в доступной степени; повторить критичные Telegram-сценарии T01–T36 из существующего QA-набора. Проверить пустые/устаревшие объявления, ошибки сети, блокировщики рекламы, очень узкие/широкие экраны, карты с большим количеством маркеров и доступность кнопок. Проверить бандл, изображения, Web Vitals и реальную задержку API. Нагрузочный smoke выполнить на тестовом окружении; не нагружать живой VPS без отдельного одобрения.

**Приёмка:** полный публичный пользовательский сценарий проходит; авторизованные Telegram-сценарии работают; консоль и сеть не содержат неожиданных `401`, смешения пользователей или фатальных ошибок; замеры быстродействия и ограничения перечислены в QA-отчёте.

### 6. Отдельный продакшен и безопасный откат

**Работы:** создать Pages deployment из существующего репозитория и `webapp/`, назначить публичный `VITE_API_URL`, `VITE_POSTHOG_API_KEY` и явный web-режим; подключить созданный владельцем поддомен, HTTPS и SPA fallback. Проверить фактические настройки CORS для обоих доменов и локальных окружений без открытия привилегий. Включить базовые HTTP security headers, favicon, метаданные общего сайта, robots/sitemap по согласованной политике индексирования, страницу политики конфиденциальности/аналитики. Сначала проверить Pages Preview, затем поддомен и реальные мобильные сценарии, с возможностью возврата к предыдущему Pages deployment. Уточнить, когда push в `main` автоматически обновит Telegram Mini App; проверить оба интерфейса до общего релиза.

**Приёмка:** HTTPS-сайт доступен без Telegram, на новом домене открывает прямые ссылки и работает с действующим API, события поступают в dashboard, ошибки и скорость контролируются, известна точная процедура отката. Не требуется копировать или пересоздавать продовую SQLite.

## Решения до начала реализации

1. **Адрес:** целевая схема по предпочтению владельца: `homeasy.rustycat.cc` — публичный сайт, `tma.rustycat.cc` — Telegram Mini App. Сначала переназначить Telegram Mini App на `tma`, только затем переключать основной домен; убедиться, что DNS и Pages-проекты это допускают.
2. **Saved без аккаунта:** рекомендовано хранение в `localStorage` в первом релизе; регистрация и синхронизация потребуют отдельного способа входа и серверной модели пользователей.
3. **Публичный сайт и поиск:** рекомендовано сразу поддержать прямую ссылку на объявление; индивидуальные поисковые карточки с динамическими OpenGraph/SEO-метаданными отложить до определения реальной потребности в SEO и шаринге.
4. **Деплой:** рекомендовано отдельное Cloudflare Pages окружение/проект от того же исходного кода для раздельных настроек и отката; окончательно выбрать после проверки текущего CF проекта и ветки.
5. **Аналитика:** рекомендовано использовать уже существующий PostHog-проект с `surface` для сравнения двух каналов; необходимость отдельного проекта, consent-механики и сроков хранения определить по реальной конфигурации и требованиям приватности.

**Базовый scope первого релиза:** этапы 1–6, включая аудит/дашборд PostHog, без пользовательской регистрации и без нового сервера. Работы можно начинать после согласования направления и адреса; публикация на внешнем домене отдельно проходит согласованный release/rollback контроль.

### 1. Модель двух окружений из одной кодовой базы

1. Оставить `webapp/` единым React/TS/Vite приложением с общими компонентами, типами DTO, запросами к API и стилями. Два конфигурируемых target/build: `web` и `telegram`; выбрать минимальный способ разделения (Vite mode / env / entry), опираясь на текущую сборку.
2. Для общего кода выделить узкую платформенную прослойку, например `runtime` / `platform`, с методами инициализации, открытия внешней ссылки, навигации, сохранения избранного и доступа к пользователю. Не расширять интерфейс сверх реально используемых операций.
3. В web-режиме исключить безусловную загрузку `telegram-web-app.js`, обращения к `window.Telegram` и auth bootstrap через `initData`. Не отправлять пустой `initData` как притворную авторизацию. В Telegram оставить текущую инициализацию, BackButton, тему и поведение открытия ссылок.
4. В обоих режимах читать **один** публичный API с **одной** продовой SQLite на существующем VPS. Не заводить второй backend, базу пользователей или отдельный каталог.
5. Проверить текущие CORS и authentication/authorization границы. Web-доступ к чтению не должен открывать админские функции или серверные Telegram-only endpoints.

**Приёмка:** web build открывает каталог без Telegram и ненужных `401`; Telegram build продолжает привычный старт, фильтры, сохранения и возвраты; компоненты не продублированы.

### 2. Пользовательские сценарии браузерного сайта

1. Лента: первая загрузка, пустая выдача, подгрузка следующей страницы, обновление, поиск, все текущие фильтры и сортировка; одинаковая семантика `4+ BR`, категорий, бюджета, локаций, неизвестных значений и карты в обоих режимах.
2. Карта OpenFreeMap/MapLibre: открытие, кластеры, выбор маркера, переход в карточку и обратно; фильтры карты соответствуют ленте. Мобильное поведение и большие desktop-экраны; не менять картографического провайдера без реальной причины.
3. Карточка: галерея, превью, адрес/география, особенности, стоимость, источник, контакты; корректные состояния `loading`, не найдено, устарело, ошибок сети. При повреждённой/протухшей внешней фотографии нужен fallback и отсутствие сломанной верстки. Само обновление CDN-ссылок и инвентаря не входит в задачу.
4. Контакты: на обычном сайте `tel:` для звонка, корректная ссылка WhatsApp (web/app fallback), Telegram username/ссылка с web fallback при отсутствии приложения. Не делать вызов Telegram bridge из web. Контакты могут быть реально несуществующими у источника — это особенность данных, а не обязательно дефект UI; логировать именно клик.
5. Избранное: web-гость хранит `publicRef` в версионированном ключе `localStorage` (валидация/дедупликация, обработка storage disabled/corrupt), сердечки синхронны в feed/map/detail/Saved и переживают reload. На повторном открытии объект вытягивается из API; удалённый/недоступный объект не ломает весь список. Telegram остаётся на существующих защищённых серверных favorites.
6. UX: понятно обозначить HomeEasy как браузерный каталог, оформить собственные favicon/title/description, логичные header/footer, loading/empty/error states и retry. Keyboard focus, Escape/Back и screen-reader labels для модальных окон, доступность кнопок и корректные tap-targets. Минимальные адаптации для desktop без переписывания дизайна.

**Приёмка:** посетитель на чистом Safari/Chrome может найти объект, посмотреть фото/карту, сохранить, обновить страницу и нажать способ связи без Telegram-аккаунта. На узком телефоне нет горизонтального скролла, недоступных CTA и интерфейса «только внутри Telegram».

### 3. Web URL, deep links и разделение источников трафика

1. Главная `/` и прямой URL карточки `/listing/:publicRef`. Существующий API поддерживает карточку по `publicRef`; использовать его, не проектировать новый REST-ресурс без необходимости.
2. Открытие карточки добавляет корректный history entry, закрытие использует ожидаемую навигацию; browser Back/Forward, прямой переход и refresh по вложенному URL обязательны. В Telegram маршрут не должен ломать BackButton и существующие `startapp` / атрибуцию.
3. Копирование web-ссылки на карточку, сохранение/чтение UTM и первоначального referrer. Поиск/фильтры в query params — по возможности минимально; обязательна стабильность URL карточки. Сохранить исходный landing URL для атрибуции, не смешивая с внутренними navigation events.
4. Не переназначать вслепую действующие `/r/:slug` и bot deep links. Проверить текущий редирект, Telegram menu/BotFather/команды и места, где зашит `homeasy.rustycat.cc`. Подготовить таблицу старый URL → новый URL/поведение; явно протестировать старые ссылки после переезда TMA.
5. Для MVP достаточно canonical/title/description общего сайта и работающих прямых ссылок. Индивидуальные серверные OpenGraph-превью, поисковая индексация всех объектов, sitemap карточек и SSR — отдельный потенциальный продуктовый этап; не объявлять готовое SPA полноценным SEO-каталогом.

**Приёмка:** скопированная карточка открывается из мессенджера или адресной строки в вебе; `F5`, Back/Forward и UTM работают; переход в Telegram из старых ссылок остаётся предсказуемым.

### 4. PostHog как измеримый MVP

1. Сначала проверить существующие `VITE_POSTHOG_API_KEY`/host, текущие события, настройки проекта, допустимый бесплатный лимит и факт поступления тестовых событий; **не создавать платную инфраструктуру автоматически**. Текущий код инициализирует PostHog с `autocapture: false` и `capture_pageview: true`.
2. Один событийный контракт с `surface: web | telegram`, `release`, `entry_point`, `referrer_domain`, `utm_source/medium/campaign` и только безопасными свойствами действия. Для web анонимная идентичность PostHog; не требовать регистрации и не отправлять персональные данные из карточек. Проверить текущий `identifyTelegramUser`: он передаёт имя и username, это стоит исключить либо отдельно обосновать и явно защитить.
3. Согласовать фактические имена событий в `analytics.ts` и трекинге перед добавлением новых. **Не дублировать** уже используемый `contact_lead_clicked`, не считать один клиентский click одновременно двумя «лидами». Распределить события: вход, каталог загружен/ошибка, поиск/фильтр/сортировка, карта/маркер, просмотр карточки, Save/Unsave, контакт с типом канала, открытие первоисточника. Не писать в аналитику raw query, phone, Telegram username, чужой FB profile URL и весь текст объявлений.
4. Обрабатывать page view при SPA-переходах ровно один раз (учесть автоматический PostHog pageview, StrictMode, двойные эффекты). Счётчик `listing_opened` трактовать как просмотр UI; существующий Telegram-authenticated `/view` не вызывать от гостя. Ошибки PostHog не должны блокировать переходы, рендер, поиск или контакты; adblocker допустим.
5. Собрать dashboard: уникальные анонимные посетители / сессии / new vs returning; `web` vs `telegram`; landing+referrer+UTM; фильтры/карта; топ карточек; последовательность `app_loaded -> catalog_loaded -> listing_opened -> contact_lead_clicked`; доли сохранений и кликов, ошибки/медленная загрузка. Оговорить: click = интерес, продажа/аренда никак автоматически не подтверждается.
6. Подготовить публичную privacy/analytics страницу и решение о consent/opt-out/cookies с учётом фактических настроек PostHog и применимых требований. Убедиться, что `VITE_*` значения публичны и не содержат приватных токенов. Проверить PostHog в preview и после доменной миграции.

**Приёмка:** на тестовом визите видна понятная воронка с `surface=web`, адекватные counts без дублей, корректное различие Telegram/web; нет явных PII в payload; полный user flow работает при недоступном PostHog.

### 5. QA, устойчивость и эксплуатационные метрики

1. Unit/integration tests: platform detection, web without Telegram SDK, guest vs authenticated requests, Saved/localStorage invalid/disabled, direct listing URL + back, contact fallback URLs, analytics schema/event count, 404/401/500/offline/timeout handling.
2. Браузерный E2E через реальные доступные Chrome и Safari/мобильные окружения: новая сессия, каталог, фильтр, карта, карточка, контакты, сохранение, refresh, Back/Forward, пустая выдача, ошибочное фото, 404, потеря сети, блокировка PostHog, узкий/широкий экран. При необходимости провести безопасный нагрузочный smoke в изолированном окружении, отдельно согласовав реальную нагрузку на прод.

### 6. Поддомены и безопасный release-порядок

Схема **целевая**, фактические DNS и Pages bindings сначала выяснить на read-only проверке:

| Адрес | Назначение после релиза | Статус на этапе плана |
| --- | --- | --- |
| `homeasy.rustycat.cc` | публичный Web App для гостей | сейчас используется Telegram Mini App; переключать последним |
| `tma.rustycat.cc` | текущий Telegram Mini App | новый custom domain, подготовить первым |
| `api.rustycat.cc` | тот же Fastify API → та же SQLite | сохранить существующий backend |

1. Установить фактические Cloudflare Pages project/build output/production branch и env, записи DNS, bot `WEBAPP_URL`, Telegram Menu Button/BotFather deep links, API routing и old tracking redirect. Не гадать по локальным конфигам; проверить live доступ/response отдельно.

Старый `homeasy` пока остаётся доступен — возможность отката сохраняется.

Не менять production API/SQLite без обнаруженной и обоснованной необходимости; если такая необходимость появится, отдельно сделать backup/restore rehearsal и безопасный rollout согласно проектным runbooks.

## Распределение работ между субагентами

**Интегратор (главный агент)** владеет архитектурой, общим `App.tsx`, платформенными API и итоговой сборкой/публикацией. Остальные агенты получают ограниченные самостоятельные области, список допустимых файлов и формулируют изменения и тесты без одновременной правки `App.tsx`/основного routing/state. Избежать write-конфликтов; отдельные worktree/ветки использовать только после проверки грязного дерева и зависимости от текущих незакоммиченных изменений.

| Фаза | Субагент | Изолированная задача / результат | Зависимость |
| --- | --- | --- | --- |
| Recon (параллельно) | A — frontend | карта связей Telegram bridge, Saved, App state, фильтры, карта | нет, read-only |
| Recon (параллельно) | B — backend/безопасность | GET/mutation auth, CORS, `/r/:slug`, bot WEBAPP_URL и инварианты одной SQLite | нет, read-only |
| Recon (параллельно) | C — analytics/privacy | существующие PostHog события, payload, дубли/PII, схема dashboard | нет, read-only |
| Recon (параллельно) | D — deploy/QA | Pages/доменный migration map и существующие E2E сценарии | нет, read-only |
| Implementation | Интегратор | platform split, web bootstrapping, общие interfaces, интеграция App | по результатам Recon |
| Implementation (параллельно) | A | изолированный Saved adapter и tests без общего App | interface зафиксирован |
| Implementation (параллельно) | B | routing/history/deep-link helper и tests | interface зафиксирован |
| Implementation (параллельно) | C | analytics service и schema/dashboard notes/tests | interface зафиксирован |
| Implementation (параллельно) | D | web UX/accessibility/CSS в отдельных компонентах + QA fixtures | interface зафиксирован |
| Integration | Интегратор | объединение изменений, конфликтов, сквозных flows, сборка двух профилей | агенты закончили |
| Acceptance (параллельно) | QA 1/QA 2/QA 3 | web E2E, Telegram regression, analytics/network/security checks | интегрированный preview |
| Release | Интегратор | production checklist, dependency order, deployment/rollback verification | QA accepted, внешняя публикация одобрена |

Каждый субагент передаёт: проверенные файлы/символы, что изменено, какие тесты запускались и их фактический результат, оставшиеся риски. Дублирование полной системы тестов и «параллельное переписывание одного файла» не допускаются. Число агентов адаптировать к реальной независимости задач; 2–4 read-only аудитора полезнее, чем четыре конфликтующие реализации.
