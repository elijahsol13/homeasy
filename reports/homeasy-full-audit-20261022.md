## E. Реестр дефектов, отклонений и рисков

### Дефекты, подтверждённые статическим путём исполнения (runtime-последствия отдельно не воспроизводились)

**DATA-01 / P1 / высокий — Facebook преждевременно исключает посты из повторной обработки.** В `src/modules/parser/facebook.scraper.ts:1014-1017` отбираются только отсутствующие в `recentPostIds` записи и не более десяти (`maxPosts` при штатном вызове, строка 1479). Затем `:1032-1049` парсит лишь эту порцию, но `:1052-1058` записывает **идентификаторы всех перехваченных постов**, включая необработанные и неудачно распарсенные. Вызов `ingestFacebookGroupListings` следует **после сохранения этого состояния**, в `:1479-1489`. `src/modules/parser/fb-state.ts:4-8,23-27` объявляет `pendingQueue`, но этот путь не наполняет и не вычитывает её. **Условное воспроизведение из кода:** перехватить 15 новых ID при `maxPosts=10` либо смоделировать ошибку ingest после сохранения состояния; при повторном обходе этих же ID фильтр объявляет их старыми. Следствие — возможен пропуск публикаций без последующего ingest; при выпадении ID из окна 50 записей или иной повторной обработке последствия могут измениться, поэтому утверждение о *необратимой* потере данных не доказано. **Уверенность высокая для дефекта управления состоянием, средняя для live-масштаба.** Направление отдельного исправления: подтверждать обработанными только успешно доведённые до ingestion ID, сохранять остаток и повторять ошибки; проверить на изолированной фикстуре «15 новых / cap 10 / ошибка ingest».

**DATA-02 / P1 / высокий по согласованности хранения — обновление проверенного GPS не переносится в физическую canonical property.** `src/modules/parser/ingestor.ts:601-604` выявляет изменение координат входящего Khmer24 факта, но `src/modules/parser/canonical-dedupe.ts:920-929` обновляет `canonical_listings.listing_facts_json`, а у связанной `canonical_properties` — только времена наблюдения. Даже полная пересборка по canonical key (`:1112-1118,1130-1132`) передаёт `null,null` как latitude/longitude, а `ON CONFLICT` не обновляет их. **Граница влияния:** `src/database/repositories/canonical-listing.repo.ts:404-436` при чтении сначала берёт валидные `facts.latitude/longitude`, затем property и Maps URL. Поэтому утверждать, что каждый новый GPS отсутствует на карте, **нельзя**: отображение иногда корректно при сохранении несогласованной колонки. Подтверждён именно дефект согласованности канонической физической записи; по реальным данным масштаб не измерен. Направление: согласовать первичный источник GPS, provenance и правила обновления физической записи; проверить расхождения на отдельной fixture и в разрешённом read-only data QA.

### Дефекты backend, воспроизведённые изолированными HTTP-запросами

**API-01 / P2 — legacy list игнорирует выбранный кластер карты.** Шаги: поднять Fastify с временной SQLite `:memory:` и одним доступным legacy-объявлением, выполнить `GET /api/v1/properties?map_cluster_key=siem_reap:absent`. Изолированный `app.inject()` вернул `total=1` при legacy read path и `total=0` в canonical. `src/modules/api/routes/properties.routes.ts:147-169` применяет фильтр только если `readPath === 'canonical'`; UI передаёт ключ в `webapp/src/services/api.ts:32-45`. Следствие: кластер→список может показать чужие объекты при legacy/rollback. Направление: единый контракт или осознанный явный запрет режима, регрессии для обоих путей. **Доказательство runtime:** локальный Fastify/fixture; **production legacy не подтверждён**.

**API-02 / P2 — legacy tracking теряет цель ссылки canonical.** Шаги: создать tracked link с `listing_public_ref=lst_...`, вызвать `POST /api/v1/links/:slug/opened` при legacy и canonical read paths. Изолированно: `listingTarget=null` в legacy, публичный `lst_...` в canonical. `src/modules/api/routes/tracking.routes.ts:110-128` разрешает ref только в canonical, а ветка legacy срабатывает лишь если `!link.listing_public_ref`. `webapp/src/App.tsx:45-69` использует ответ для открытия карточки. Последствие — deep link без карточки в совместимом legacy режиме; production currently canonical. Направление: контрактная обработка canonical refs независимо от пути чтения или явное корректное fallback поведение.

**API-03 / P2 — 500 вместо клиентской ошибки для неизвестной canonical-ссылки.** Шаги: admin `POST /api/v1/links` с несуществующим `listingPublicRef`. `src/services/tracking.service.ts:28-33` бросает обычный `Error('Unknown canonical listing public_ref')`, `src/modules/api/server.ts:92-99` отображает его в 500.
