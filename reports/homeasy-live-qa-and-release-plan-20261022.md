## Задание QA-агенту: реальный пользовательский прогон

**Цель:** дать владельцу честный и воспроизводимый ответ, какие функции работают в реально доступной версии Homeasy. Использовать [существующие 36 кейсов](miniapp-manual-test-cases-20261016.md) (T01–T36) как основную матрицу, дополнив только следующими регрессиями. Не выдавать юнит-тесты или исходный код за фактические пользовательские клики.

**Порядок запуска:**

1. Зафиксировать текущую дату/часовой пояс, URL, тип клиента (обычный desktop Chrome / авторизованный Telegram Web / мобильный Telegram), роль пользователя, commit/deployment ID и hash скачанного JS. Сначала сравнить источник тестирования с `main` и текущей Pages production branch: статус относится только к **конкретному билду**. Если проверяется Preview — явно отметить Preview; результаты production не переносить на Preview и наоборот.
2. Открыть `https://homeasy.rustycat.cc/` через действительно подключённый Chrome, пройти T03–T26 и T29–T30, T36 в доступных условиях. Для каждого действия измерить видимый результат, соответствующий API, фактическую сортировку/фильтры, ошибки в Network и Console, скриншот при FAIL. Проверить и «обычную» ленту, и пустую выдачу, reload, назад, переход в деталь и контакты без выполнения звонков/отправки сообщений.
3. В **том же подключённом Chrome после ручного входа владельца в Telegram Web** открыть чат `@Homeasy_kh_bot`, запустить Mini App из бота и пройти T01–T02, T27–T33. Проверить Telegram user context, Saved add/remove/reload, deep links (при наличии безопасного тестового `publicRef`), отсутствие модерации у обычного пользователя и админскую видимость в предоставленном тестовом аккаунте. Вернуть избранное к исходному состоянию. Не записывать cookies, Telegram initData, токены или PII в отчёт.
4. Повторить ключевые тесты на **кандидате с исправлениями из `main`** в безопасном preview/staging или после согласованного релиза: T14, T17, T19, T23–T26 и регрессии R01–R06 ниже. Обязательно отдельный результат для прямого Web и Telegram Web, не считать старые FAIL уже исправленными без настоящих кликов.
5. Сформировать единую матрицу: `ID | среда/версия | шаги | ожидание | факт | PASS/FAIL/PARTIAL/BLOCKED/N/A | screenshot/API/publicRef | severity`. Писать `BLOCKED`, если нет управления нужной вкладкой, тестовых ссылок или соответствующей роли. У каждого FAIL — точные действия, ожидаемое/фактическое и воспроизводимость. Не выводить общее «всё работает» из короткого smoke.

**Новые проверки поверх T01–T36:**

| ID | Реальные действия / критерий |
| --- | --- |
| R01 | `Newest`: на 2+ страницах дата **публикации оригинала** у более новой карточки должна идти перед старой (не дата последнего scraper sighting); проверить конкретные `publicRef` и видимые даты. |
| R02 | `4+ BR`: в ленте отсутствуют карточки с `null`, 0, 1, 2, 3 BR; показать пару проверяемых `publicRef`; комбинированные фильтры не ломаются. |
| R03 | Применить один и несколько фильтров (4+ BR, location, price, type, pool), открыть Map, проверить `/map` query и набор/число предложений относительно filtered feed; Map → cluster → View as list сохраняет фильтры. Учитывать viewport карты при сравнении чисел. |
| R04 | Проверить реальную загрузку OpenFreeMap Liberty: tiles/style без сетевых 4xx/5xx, подписи EN/Latin где доступно, пан/зум, маркеры и возврат к ленте. |
| R05 | Быстрая смена search/sort/filter во время запросов, `Load More` одновременно со сменой условий, быстро открыть два detail, сохранить/снять Saved: последнее действие побеждает, нет чужих карточек/зависших loading. |
| R06 | Повторные посещения Web и Telegram: возврат к выбранному объявлению/deep link, guest/auth разделение, восстановление фильтров после reload, карта и лента после переключения вкладок. |

**Ограничения:** никаких live scraping, платных LLM, перезапусков, миграций, изменений Cloudflare Pages или live SQLite. T34–T35 (одобрение/отклонение) выполнять только с заранее подготовленными тестовыми объявлениями и отдельным разрешением на их изменение; при их отсутствии — BLOCKED. Не подменять реальный Telegram Web локальным эмулятором initData.

**Критерий готовности к релизу:** каждый P0 имеет PASS на целевой версии либо согласованный владельцем конкретный риск; существенные P1 имеют PASS или оформлены как известный дефект со степенью влияния. Выполнены отдельные поверхностные проверки после выкладки (feed/detail/filter/map/deep link/Saved) и зафиксирован точный deployment ID. Неопровергнутый FAIL старого релиза, отсутствие авторизации или непроверенный кандидат означают **результат QA не полный**, а не автоматическую блокировку всей разработки.

## GitHub → Cloudflare Pages: предлагаемое единое правило

Текущая схема «`main` — разработка, `feature/telegram-mini-app` — продакшен» **технически допустима** и уже подтверждена как намеренная. Долгоживущая `feature/*` в роли production создаёт путаницу: агенты снова воспринимают ожидаемое расхождение как аварию. Пока схема официально не изменена, QA/аудит обязан писать «ожидаемое отставание до релиза» с двумя commit SHA и **не назначать исправление самопроизвольно**.

**Рекомендуемый после QA вариант:** `main` — единственная постоянная production-ветка; изменения живут в коротких `feature/*`, тестируются в Cloudflare Pages Preview и вливаются в `main` только после готовности релиза. Cloudflare Pages production branch = `main`. Защитить `main` от нерассмотренных прямых push и привязать merge к QA-гейту. При таком выборе push в `main` означает разрешение на публикацию; это изменение текущей привычки работы.

**Переход (только отдельный согласованный релиз):** (а) QA кандидата `main`; (б) зафиксировать Pages настройки/текущий production deployment/rollback и SHA; (в) включить проверки перед merge; (г) переключить Pages production branch на `main` и проверить публикацию и Telegram bot entry/deep links; (д) удалить или заархивировать `feature/telegram-mini-app` **лишь после** подтверждения работающего нового пути и rollback. До этих действий сохранять существующую ветку. Никакие Git/Pages настройки данным документом не изменены.

Если владелец предпочитает свободно пушить в `main` без автоматического релиза, безопасный второй вариант — две **честно названные** постоянные ветки `main` (разработка) и `production` (только одобренное продвижение), Cloudflare Pages = `production`. В этом случае различие SHA *нормально по определению* и не является дефектом. Выбор схемы нужен один раз; после выбора зафиксировать его в `agent_docs/decisions.md` и `project_progress.md`, чтобы следующие агенты не пересматривали архитектуру.
