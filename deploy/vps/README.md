# Homeasy — Singapore VPS cutover runbook (prepared, NOT executed)

**Пошаговая инструкция для владельца (на русском, с командами и откатом): [OPERATOR_GUIDE_RU.md](OPERATOR_GUIDE_RU.md).** Пример настроек VPS без секретов: [env.vps.template](env.vps.template).

Target: Ubuntu/Debian Linux VPS, **2 vCPU / 4 GiB RAM / ~40 GiB NVMe**. Cloudflare Pages still hosts the frontend; the VPS hosts API, Telegram bot, Khmer24 worker, SQLite, local backup worker and Cloudflare Tunnel. Bright Data tools are **manual/on-demand** and may be invoked on the VPS later under a separately approved provider/cost scope. Facebook/Camoufox with its **macOS fingerprint, account and residential IP remains only on the Mac**.

Bright Data utility scripts are **not bundled into the slim production Docker images**. An approved on-demand VPS run will need a separate Node environment with the repository's development dependencies (`npm ci`) or another explicitly configured runner, plus provider credentials supplied outside Git. No automated Bright Data schedule is part of this migration.

This is a manual deployment procedure, not authorization to modify the active installation. Current Compose is intended for the VPS: running `docker compose up` on the old Mac may replace the currently running worker with a Khmer24-only VPS worker. Do not do that during preparation.

## Prep / minimum infrastructure

1. Verify this source and its required commits are actually on the intended GitHub branch. The developer working tree may contain other unfinished changes; do not assume that `git status` is clean or that a push already happened. Review a scoped commit/release separately.
2. Ensure the server has a supported Linux distribution, Docker Engine + Compose plugin, Git, curl, enough free storage and working IPv4/IPv6 outbound connectivity. Keep Docker bound to the host and SSH access protected; API is already published only on `127.0.0.1:3000`. The Cloudflare Tunnel is the public entry point. Configure automatic OS security updates if the host does not have them.
3. Confirm free space with `df -h` and RAM with `free -h`; 40 GiB is plausible but browser binary, Docker build layers, SQLite, backups and media can grow. Do not transfer old report caches or bulk historical backup folders unless explicitly needed.
4. Prepare the secrets **on the VPS**, not in Git: a host `.env` with current `BOT_TOKEN`, other actually used API keys and runtime settings, and a newly generated 32+ character `FB_INGEST_TOKEN`. Configure the same token in the Mac `.env` later. Set `LISTING_READ_PATH=canonical` and expected bot mode. **Do not set `FB_INGEST_URL` in the VPS `.env`.** The Compose environment sets `HOMEASY_DEPLOYMENT_ROLE=vps` for services. Protect files with mode 0600 and use a non-root deploy account with access to Docker.
5. Prepare `deploy/cloudflared/config.yml` and its existing named-tunnel credential JSON outside Git. Verify the tunnel configuration routes `api.rustycat.cc` to API service `http://api:3000` from inside the Compose network, and that the public DNS route is already in place. Do not expose port 3000 publicly or create a new tunnel/DNS record without a deployment decision.

## Safe data migration and switchover (at an authorized cutover)

1. Take and verify a **SQLite-native consistent snapshot** on the current Mac using the existing `src/database/backup.ts` workflow (`npm run db:backup`). Check its SHA-256 and `PRAGMA integrity_check` against an isolated copy. **Never copy live `homeasy.db` by itself while its WAL may contain committed transactions; never network-mount SQLite between hosts.** Keep an untouched rollback snapshot.
2. At the agreed handover point, **stop the old Mac API, bot, Khmer24 worker and backup writer** before the final snapshot. Preserve the Mac database, WAL/SHM, secrets and rollback files. Take a final verified snapshot after writers stop, record its hash, and select that exact snapshot for transfer. Do not restart the old polling bot or old server writers while the VPS is serving traffic. The old Mac Cloudflare Tunnel connector must also be stopped before the new VPS tunnel begins serving the same named tunnel; concurrent connectors could route some public requests back to the stopped Mac API.
3. Clone the approved commit on the VPS and enable the existing hook: `git config --local core.hooksPath .githooks`. Create `data/` and transfer **only the selected verified SQLite `.db` snapshot** to a temporary filename on the VPS. Verify the transferred SHA-256; only then install it as `data/homeasy.db` with appropriate owner/mode. Backups produced by the VPS remain under `data/backups/`; make sure the first independent snapshot succeeds. Preserve the previous source DB unchanged for rollback.
4. Transfer the needed `.env`, Cloudflare Tunnel files and other explicitly identified non-Facebook operational configuration separately over SSH. **Do not copy** `data/fb_session.json`, `data/fb_device.json`, `data/fb_safety_state.json`, `data/fb_runtime.lock`, `data/fb_outbox/` or a full Mac `data/` tree. The `fb_outbox/` queue remains on the Mac until acknowledged by the VPS.
5. Build images on the VPS (`docker compose --parallel 1 build` if supported by the installed Compose version). The scraper image still installs Camoufox because **Khmer24 also depends on Camoufox**; the VPS worker entrypoint and runtime role deliberately prevent Facebook automation. Under 4 GiB, building may be the heaviest moment: inspect swap/available RAM before trying further optimizations.
6. Start API and backup with `docker compose up -d api backup` and check the local API. Stop the **old Mac tunnel connector** at the agreed switch point, then start the VPS connector with `docker compose up -d tunnel`. Start the **single** Telegram polling bot using `docker compose up -d bot` after verifying the public API. Be careful that Compose `depends_on` can automatically start API. Do not run two bot instances with the same token; confirm polling/webhook mode and existing Telegram settings.
7. Check `docker compose ps`, `curl -fsS http://127.0.0.1:3000/health`, `curl -fsS https://api.rustycat.cc/health`, canonical listing/filters routes, bot messages, and `docker compose exec -T backup node dist/database/backup-worker.js --health` after a backup has completed. Confirm public Pages at `homeasy.rustycat.cc` still calls the VPS API. Check SQLite integrity on an **isolated snapshot** if needed, not on a live writable DB through a migration shortcut.
8. **Khmer24 datacenter egress is still unverified.** Only after an approved bounded VPS smoke test shows actual listings can be read from Singapore, start `docker compose up -d scraper`. A working Mac/residential Khmer24 flow does not prove that a datacenter IP works. Do not enable paid provider dispatch as a substitute without separate authorization.
9. Configure on the **Mac only**: `FB_INGEST_URL=https://api.rustycat.cc/api/v1/internal/facebook/ingest` and matching `FB_INGEST_TOKEN`. Run `npm run scrape:fb:smoke -- --group=0` only when the existing Facebook safety state permits a user-approved attended smoke. Successful batches enter the VPS canonical SQLite through authenticated `POST /api/v1/internal/facebook/ingest` (max 10 posts/1 MiB); transient failures remain in private `data/fb_outbox/`. Replay with `npm run fb:flush-outbox` **without starting the browser** when needed. Keep the pinned Mac fingerprint/account and its local Camoufox setup untouched. Once the combined Mac worker is stopped, run normal Facebook collection separately with `npm run scrape:fb` on the Mac when desired; a periodic Mac-only schedule has not been installed. Existing local Facebook feed-reparse/freshness commands are intentionally disabled in remote-ingest mode because their writes still target local SQLite; remote freshness needs a future scoped design if required.

## Resource monitoring and recovery

- No explicit Docker `mem_limit`, Compose memory quota, or Node `--max-old-space-size` restriction is set. **Docker and Linux can still OOM-kill a process under host-wide memory pressure**; inspect `docker stats`, `free -h`, `dmesg`/`journalctl` and restarts before setting quotas. Do not prematurely add a metrics service.
- Run `bash scripts/vps-status.sh` on the VPS for a **read-only status snapshot**: host RAM/disk, five Compose services, container CPU/RAM/PIDs, API health, snapshot freshness. Nonzero exit means investigation is needed. Suggested manual inspection: daily for the first week, then weekly. Watch a sustained >85% disk usage, swap/OOMs, restart loops, unhealthy backups (>24h) and recurring API/Khmer24 errors.
- Backups are verified `VACUUM INTO` snapshots on the **same VPS disk** every 12 hours; this protects against SQLite corruption and routine rollback but **does not protect against total VPS/disk loss**. Existing agreed MVP RPO is up to 24 hours. Off-host backup is a separate future decision; do not state it is configured.
- On a failed cutover, stop VPS writers and Telegram polling, preserve VPS files for diagnosis, restore the *untouched Mac installation* with its prior DB/WAL and credentials, and restore the original tunnel routing only under the agreed operational procedure. Avoid running both writer sets simultaneously or trying to merge divergent SQLite files.
