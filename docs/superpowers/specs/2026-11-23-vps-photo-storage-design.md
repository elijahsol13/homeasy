# Homeasy: локальные фото на VPS и очистка

Статус: согласованное направление, 2026-11-23. Владелец выбрал хранение на существующем VPS, лёгкую конвертацию, порог очистки 90 дней после выхода объявления из публичного каталога и тот же срок после загрузки для никогда не опубликованных фото. Копий фото вне VPS пока не будет; потеря диска VPS означает потерю этих файлов. Локальная реализация следует этому проекту. Выпуск, массовое посещение Facebook, загрузка фото и изменение production SQLite требуют отдельного релизного объёма.

## Задача и границы

Обеспечить стабильную выдачу полной, подтверждённой источником галереи Facebook без истекающих CDN-адресов. Первый охват — Facebook; Khmer24 остаётся на нынешних URL до отдельной проверки. Facebook/Camoufox и закреплённая сессия остаются на Mac, API и файлы — на VPS. Оригинальные записи источника, модерация, идентификаторы объявлений и порядок фото сохраняются. Исторические фото нельзя сопоставлять с новыми только по количеству или части CDN-имени (reports/homeasy-camoufox-one-post-gallery-20261122.md).

## Выбор подхода

- Обновлять CDN-ссылки через HTTP: мало кода и места, но ссылки снова истекают, а доказано восстановление максимум первой фотографии части постов. Не решает цель полной стабильной галереи.
- Хранить изображения в SQLite: согласованность с существующим backup проще, но каждая из 21 полных копий базы дублировала бы все фото, увеличив расход диска и WAL.
- Хранить WebP-файлы на диске VPS и метаданные/связи в SQLite: выбранный владельцем путь. Нужны аккуратная очистка и согласование с backup/rollback; отдельный сервис и S3 не добавляются.

Для очистки простое удаление на 30-й день противоречит 30-дневному правилу публичной видимости и возможности повторного появления. Удаление только файлов без ссылок не чистит фотографии скрытых объявлений, так как исходная история остаётся. Выбрано правило публичной видимости + 90 дней + проверка ссылок.

## Приём, хранение и выдача

1. Узкая Mac-операция получает фото только подтверждённого исходного поста после проверки post/group identity и готовности галереи. Текущий сборщик продолжает извлекать URL без общего скачивания бинарных ресурсов браузером. Конкретные выбранные фото скачиваются и конвертируются отдельно на Mac; этот путь нельзя включать обычным запуском без согласованного режима.
2. Уже установленный sharp делает WebP для просмотра (ориентир: длинная сторона не более 1600 px, качество около 75) и миниатюру (400 px). EXIF удаляется. Это стартовые параметры: качество и реальные байты нужно проверить на репрезентативных исходниках до выпуска. Исходные бинарные фото постоянно не сохраняются.
3. Mac отправляет ограниченные файлы и пару group_id + post_id в новый аутентифицированный API-маршрут. VPS находит ровно один FACEBOOK_GROUP source item по group_id, external_id и проверенному исходному URL; неоднозначность отвергается. source_item_id — внутренний ID VPS и с Mac не передаётся. VPS проверяет размеры, тип и фактическую сигнатуру файла, сервер сам назначает путь внутри игнорируемого Git каталога data/media; временный файл переименовывается атомарно. Токен и содержимое не попадают в логи. Повторная доставка идемпотентна по hash и source identity.
4. Отдельные hosted-media метаданные в SQLite связывают хэш файла с source item, gallery version, порядковым номером и подтверждённым photo anchor ID, когда он доступен. Версия галереи публикуется атомарно; существующий unique(media_asset_id, source_item_id) не используется как ключ нескольких версий. Файл с тем же хэшем может иметь несколько связей и удаляется только после проверки всех связей. Публичная выдача возвращает hosted URL только для подтверждённых связанных фото. Новую текущую галерею можно опубликовать как новую версию исходного поста после полной проверки, но нельзя тихо перезаписать позиции октябрьских фото, соответствие которых не доказано. Неполная/непрогрузившаяся галерея не заменяет прежнюю.

## Очистка и восстановление

- Использовать то же условие публичной видимости, что и каталог: статус, доступность, модерацию и 30-дневную свежесть исходного предложения. В существующем 12-часовом backup worker после успешного снимка отмечать дату первого выхода объявления из публичной выдачи. При возвращении в выдачу дату сбрасывать. Для уже скрытых на момент выпуска объявлений отсчёт начинается с первого достоверного сканирования после выпуска, без выдуманной исторической даты. Для фото объявления, которое ни разу не стало публичным, отсчёт 90 дней начинается от первого успешного приёма файла. Статус Pending сам по себе не продлевает хранение. Подтверждённая новая существенная редакция источника сбрасывает отсчёт по тому же правилу, что и публичная свежесть.
- Через 90 полных суток отсутствия публичной связи пометить связь с локальным файлом как неактивную. Файл, используемый другой публичной карточкой, остаётся. Исходные source items, URL и история не удаляются.
- После пометки держать байты ещё минимум 14 суток. На 104-й день, после ротации снимков, содержавших активные связи, удалять связи галереи. После удаления последней связи начинать новый 14-дневный период для ротации снимков, которые ещё содержали ссылки на файл. Физическое удаление допустимо только если файл всё ещё не нужен ни одной связи, есть свежий успешный backup и все сохранившиеся обычные SQLite-снимки, которые могли ссылаться на файл, уже вышли из 21-снимочной ротации. Долговременная ручная rollback-точка содержит только SQLite: после физической очистки она может ссылаться на отсутствующие фото. При чтении отсутствующего файла API отдаёт управляемый 404, а каталог — исходный URL, если он доступен, либо placeholder. Это принятый риск хранения только на VPS; он не должен блокировать автоматическую очистку. При сбое backup или несогласованности DB/файлов очистка останавливается. Если объявление вернулось до удаления связей, связь восстанавливается без повторной загрузки. Итого галерея становится неактивной на 90-й день, ссылки обычно удаляются не раньше 104-го дня, а байты обычно освобождаются не раньше 118-го дня; задержки backup/ротации сдвигают сроки дальше. Старые ручные SQLite-точки могут восстановиться без уже удалённых фото.
- Битые/частичные временные файлы удалять отдельно после 24 часов; только внутри data/media и без перехода по симлинкам. Запуск сначала в dry-run, затем ограниченная партия с журналом количества/байтов. Использовать существующий backup worker, без нового cron или демона.
- Нынешний backup делает снимок только SQLite. Файлы на том же диске переживают откат базы в пределах окна очистки, но не потерю диска VPS. Владелец сознательно отложил отдельную копию фото: после полной потери диска восстановление SQLite не вернёт изображения. Релизная проверка должна явно проверить поведение карточек при отсутствующих файлах, не обещая восстановление самих фото.

## Проверка до выпуска

На временных SQLite и каталогах проверить upload/retry/обрыв, тип/размер/путь, порядок полной галереи в API, повторное появление объявления, общий файл двух карточек, дни 89/90/104/118, сбой backup, старый rollback-снимок и фактическую очистку. В локальном браузере проверить обложку и детали. До запуска на VPS измерить свободное место и WebP-размеры реальной выборки. Отдельный релиз должен сохранить прежний Docker image, Web/TMA артефакты и данные.
